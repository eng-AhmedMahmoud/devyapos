## Scope

This repository is **one deployable unit**: the public marketing site for Moving POS at
https://pos.devya.dev, a single-package Next.js 16 App Router app (next-intl, Tailwind 4,
vitest), 151 tracked files. Audited units:

- **Pages** — `app/[locale]/*`: home, features, pricing, compare, foodics-alternative,
  eta-einvoicing, hardware, how-it-works, about, contact, privacy, terms, refund, and
  **accounting-trial** (the sign-up page for the accounting product).
- **Server surface** — `app/api/lead/route.ts` (lead form → forward or on-disk outbox),
  `app/api/consent/route.ts`, `proxy.ts` (locale middleware), `next.config.ts` (headers, CSP,
  the `/api` rewrite).
- **Shared code** — `lib/` (leads, lead outbox, consent, trial, brand, analytics, JSON-LD),
  `components/`, `content/` (ar/en copy behind one typed contract).
- **Infra** — `Dockerfile`, `docker-compose.prod.yml`, `scripts/deploy.sh`,
  `.github/workflows/ci.yml`, `.githooks/pre-commit`; docs under `docs/`.

**Named but not in this repo.** The request listed moving, stores, POS, admin, accounting and
shared code. Here, *Moving* is the brand this site carries, *accounting* is the
`/accounting-trial` page (only its browser side; it posts to the ops-api control plane), and
*shared code* is `lib/`, `components/` and `content/`. The **POS, kitchen display, shop and
admin product** lives in the `bohub-pos` monorepo, **Moving Stores** in `devya-commerce`, and
the **accounting control plane** in the ops-api repo. None of those were audited here; each
needs its own X-Ray.

**How it really deploys.** Not Vercel. Since 2026-09-25 the site runs on the Devya VPS
(72.61.81.59): `scripts/deploy.sh` ships a `git archive` over SSH, Docker Compose rebuilds
container `devya-devyapos` on `127.0.0.1:3009`, host nginx terminates TLS. Several docs still
say "Vercel auto-deploys main" (finding AGL-F6 and friends). A stale copy of the old build is
still live on Vercel at devyapos.vercel.app (SEC-F3).

**In-flight work seen during the audit, left untouched.** PR #15 (move to
`pos.movingsystems.tech`, waiting on DNS and ops-api changes outside the repo) and an
unpushed local branch `feat/gdpr-policy-texts` (privacy-policy rewrite, drafts for legal
review). Fix tracks below that touch `scripts/deploy.sh`, `README.md` or `docs/spec.md` will
overlap PR #15, which will need a rebase.

## Executive summary

Moving POS's marketing site is small, carefully written code wrapped in almost no process.
At the level of a single file it is better than most: strict TypeScript with no `any`, no
lint suppressions and under 2% duplication; a privacy design that refuses third-party
scripts and is enforced by tests; a hardened edge (CSP, HSTS, a loopback-only container
running as a non-root user); and pull-request descriptions that read like engineering
notes. The X-Ray scores the site **46% health** (mean maturity **1.82 of 4** across 113
practices) with an urgency index of **62.8** — most practices sit in the "improve this
quarter" band, not because the code is poor but because nothing around it is enforced.

The headline risk is the **lead path**, which is the site's whole reason to exist. Leads
that cannot be forwarded fall into a file on one VPS volume that nothing drains, backs up or
alerts on; a read error on that file would overwrite every stored lead; and the team's own
records show roughly three and a half weeks of leads were already lost after the move off
Vercel. Second, the **framework in production carries three critical and four high Next.js
advisories**, open for up to 44 days, with no dependency scanning to announce them — none is
reachable on today's configuration, but one routine change would expose them. Third, **the
quality gates do not gate**: `main` has no branch protection, a red build was merged and
`main` stayed red for 28 days, and `deploy.sh` ships whatever `main` is without asking CI.

The adversarial `/sec` review of every server route, client form, header and deploy script
found **no exploitable vulnerability** that survived verification. Its two candidates — a
spoofable rate-limit header and spreadsheet-formula injection into the lead receiver — were
refuted: production nginx overwrites the header and the container is reachable only through
nginx, and this repo emits JSON, not cells. They become hardening notes, not findings.

Findings: **0 critical, 5 high, 30 medium, 27 low** (62), grouped into **nine fix tracks**,
one GitHub issue each (#16–#24). Security-relevant tracks come first: patch the
dependencies, make leads durable, gate deploys on CI and retire the legacy Vercel copy. 46
practices carry a `[workshop]` tag — ceremonies, stakeholder habits and on-call reality that
only a conversation can settle — and are scored conservatively until then.

**Top strengths**
1. Code hygiene — strict TS, 0 lint warnings or suppressions, 1.86% duplication, single-sourced typed content (CDH-08, ARC-04, `content/types.ts`).
2. Privacy by construction — same-origin CSP plus `tests/privacy.test.ts` refusing third-party hosts and lead PII in logs (SEC-08, ARC-11).
3. Defensive integrations — timeouts on both outbound calls, stable lead id for receiver dedupe, honest 503 with a WhatsApp fallback (ARC-09, ARC-14).

**Top risks**
1. Leads can be lost or overwritten without anyone noticing (REQ-F5, ARC-F1, ARC-F2, SEC-F2 — high).
2. Next.js 16.2.12 with 3 critical / 4 high advisories and no scanning (SEC-F1 — high).
3. CI and deploy are advisory: no protected `main`, deploys ignore CI (AGL-F1, QEN-F3, AGL-F2 — medium, systemic).

## Security review (/sec)

Scope: whole repository at `63d267b`, every file listed under *Scope* except `public/`
assets and docs. Method: one discovery agent, then one independent refutation agent per
candidate; findings below confidence 8 are dropped, as `/sec` requires.

**No vulnerability survived verification.**

| Candidate | Where | Verdict | Why it was refuted |
|---|---|---|---|
| C1 Rate-limit identity bypass via client-set `X-Real-IP` | `app/api/lead/route.ts:112-118` | 2/10, dropped | Production nginx (`/etc/nginx/sites-enabled/devya-devyapos`) sets `X-Real-IP $remote_addr`, overwriting the client's value; the container is published on `127.0.0.1:3009` only and no other vhost proxies to it. Hardening note: validate the header with `net.isIP()` and version the nginx site in the repo (PR #15 adds `deploy/nginx.conf`). |
| C2 Spreadsheet-formula injection into the lead receiver | `lib/leads.ts:133-241` → forward | 2/10, dropped | This repo emits JSON and a JSONL outbox; it builds no CSV/sheet and renders no lead field as HTML. The sink is the receiver's. Contract note added in T2: every string is raw user input. |

Checked and clean: lead and consent route validation and response bodies; outbox file naming
and permissions (no client value reaches a path); forward URL/headers (env-only); both
`dangerouslySetInnerHTML` uses (static theme script; JSON-LD escapes `<` and carries repo
data only); `searchParams`/header reflection in pages; attribution from `sessionStorage`
(reporting only, never a trust signal); the trial form's cross-origin POST (no credentials);
the `/api/:path*` rewrite (path-only, dead upstream — an availability defect, SEC-F9);
middleware matcher case handling; Dockerfile, compose, `deploy.sh` and CI for credentials on
command lines or untrusted input in `run:` steps; numeric env parsing (`Number(x) || default`
falls back on garbage rather than mis-parsing); NODE_ENV gating of CSP/HSTS (the image sets
`NODE_ENV=production`); `devya.solutions` — only the deliberate Gmail contact address
`devya.solutions@gmail.com`, no wrong domain.

What `/sec` excludes by design — outdated dependencies, missing hardening, observability,
backups — is scored in the SEC pillar below (SEC-F1, SEC-F2, SEC-F5, SEC-F8, SEC-F11).

### T1 — Patch the Next.js and sharp advisories, and turn on dependency scanning (#16)

Acceptance:
- `pnpm audit --prod --audit-level high` reports no high or critical advisory on the lockfile the Docker image installs from
- next and eslint-config-next on a patched 16.x; sharp override raised past the fixed version; @types/node matches the Node 24 runtime
- CI runs the audit step and fails on high/critical; CI and Dockerfile use the same pnpm major (packageManager field)
- .github/dependabot.yml covers npm, github-actions and docker; Dependabot alerts and security updates enabled on the repo
- lint, typecheck, tests and build green; production serves the new build

### T2 — Leads and consent receipts are never lost, overwritten or left unnoticed (#17)

Acceptance:
- A read error on the outbox can never truncate or overwrite stored leads (test proves it)
- Unforwarded leads are counted and surfaced: an operator command reports pending/total without printing PII, and the lead route logs an error-level line on every unforwarded lead
- An operator can pull an off-box copy of the outbox and consent receipts with one documented command
- Consent receipts are written to an append-only file on the persistent volume with a retention matching the policy, not only to container logs
- The forward contract matches the code (4xx retry behaviour) and carries a version field; route comments describe the VPS, not Vercel
- Tests cover each behaviour above

### T3 — Behavioural tests for the conversion path, plus a coverage floor (#18)

Acceptance:
- POST /api/lead and POST /api/consent are exercised as route handlers: valid, invalid, honeypot, rate limit, content-type, forward success/failure
- lib/leads.ts and lib/trial.ts validators have table-driven tests (phone normalisation, Arabic/Persian digit folding, trial claim answers)
- Security headers and locale routing are tested by evaluating next.config.ts / proxy.ts, not by grepping source text
- Coverage is measured in CI with a floor at the measured baseline (ratchet: may rise, never fall)

### T4 — Deploys gate on CI and prove health; slimmer image; no dead /api rewrite (#19)

Acceptance:
- The dangling /api/:path* rewrite is gone; unknown /api paths answer 404, not 500
- GET /api/health answers 200 with release id and no PII; production config is checked at boot and problems are logged loudly
- scripts/deploy.sh refuses to ship a commit whose CI is not green (override flag documented), smoke-tests /ar, /en, /api/health and the lead route's refusal of a bad request, records the release (tag + .deployed-commit) and builds with --pull
- Release backups no longer duplicate the host secrets file and are pruned to a bounded count; rollback still restores the env
- Runtime image is Next standalone output: no devDependencies or source; container healthcheck uses /api/health
- Error boundaries and onRequestError log server errors as one structured line
- public/.well-known/security.txt published

### T5 — Browser smoke journeys in CI, and the /contact hydration error fixed (#20)

Acceptance:
- Playwright smoke runs in CI against a production build: home ar/en, contact form validation (no real POST leaves the test), consent banner accept/reject, accounting-trial page renders, zero console errors
- React #418 on cold loads of /contact is reproduced, root-caused and fixed; the zero-console-error check guards it

### T6 — One locale per page bundle, shared form primitives, dead code removed (#21)

Acceptance:
- Client JS carries only the active locale's copy; content/index.ts is server-only; a CI budget fails the build if first-load JS grows past the measured baseline
- One Field primitive and one Egyptian phone rule shared by the contact form, trial form and ROI calculator
- Orphan component and unused functions removed; one digit-folding helper; the site host comes from lib/brand.ts

### T7 — Pricing claims say what they are, and WhatsApp CTAs carry a source tag (#22)

Acceptance:
- No copy calls the Foodics figures 'published'; each comparison carries a retrievedAt date and a test fails when it is older than 90 days
- Every WhatsApp CTA prefill carries a short, non-personal source code per placement
- The superseded EN privacy paragraph is removed and the parity allow-list entry dropped

### T8 — Docs match the system, decisions are recorded, and agents get repo context (#23)

Acceptance:
- No doc, comment or env example describes Vercel hosting or 'no backend'; docs/spec.md and an architecture page describe the VPS system that ships
- docs/decisions/ holds ADRs for VPS hosting, the lead outbox, the direct trial post, no third-party trackers and the product renames
- docs/testing.md states the test strategy; README describes the real test suite
- CLAUDE.md (and AGENTS.md pointer) carry the repo's working rules; an AI usage policy and a PR template with a review checklist exist; the secret-scan hook installs itself on `pnpm install`
- Open compliance actions in docs/compliance/gdpr-audit.md point at GitHub issues instead of living only in markdown

### T9 — Protect main with required CI, and retire the legacy Vercel copy (#24)

Acceptance:

## Appendix

### Formulas (methodology §6)

```
Practice Maturity Score  = (M_verified / 4) × 100
Practice Urgency Score   = P × (5 − M_verified)        P: High 3 · Medium 2 · Low 1
Domain Health %          = Σ maturity / (n × 100) × 100
Domain Urgency Index     = Σ urgency / (Σ P × 5) × 100
Engagement               = mean of pillar Health % and of pillar Urgency Index
```

### Maturity scale

| M | Label | Meaning |
|---|---|---|
| 4 | Established | Practiced consistently, evidenced in code and process artifacts |
| 3 | Emerging | Practiced, with gaps in consistency, coverage or tooling |
| 2 | Misapplied | Attempted in a way that hurts or misleads |
| 1 | Absent | Not practiced |

### Decision bands (per practice urgency)

| Urgency | Decision |
|---|---|
| 1–3 | Maintain |
| 4–5 | Monitor |
| 6–8 | Improvement backlog |
| 9–11 | Plan improvement this quarter |
| 12–14 | High risk — act now |
| 15+ | Critical (unreachable with P ≤ 3; kept for partner-scale compatibility) |

### Method

Seven pillar auditors walked every `codeEvidenceChecks` item of the `devya-xray-v1` catalog in parallel against a clean worktree of the audited commit, ran the measurable checks (lint, typecheck, tests, build, `pnpm audit`, duplication, GitHub settings, production headers) and cited evidence as `path:line`, commit or PR — never code excerpts. Priority P was set for this product: a near-static site whose job is capturing restaurant leads and trial sign-ups. The `/sec` review ran as its own phase with independent refutation agents. Scores were computed by script from the per-practice table above.
